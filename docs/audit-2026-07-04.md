## Résumé exécutif

1. **Le risque n°1 n'est pas un bug de calcul, c'est le gel.** Trois chemins d'I/O sans timeout (réponse CDP, `connectToEIS`/handshake EIS, pipe de capture KWin) peuvent chacun **figer le gate MCP pour toujours** — tous les outils deviennent alors muets, sans aucune trace exploitable puisque `adapter-cdp-webview` et `adapter-mcp-server` ne contiennent **zéro ligne de tracing**. Le sprint prioritaire est un sprint « anti-gel + observabilité », pas un sprint d'outils.
2. **La révision du SDK est nécessaire et documentée au diff près.** Les copies vendored (Chronos, Atelier) sont figées au commit M0 du 25/06 — le script de sync n'a jamais retourné depuis sa création. Chronos porte 3 commits locaux du 28/06 : majoritairement des **régressions** (backpressure supprimée, CORS retiré, handler inline) mais aussi **3 correctifs originaux de valeur jamais rapatriés**, dont un timeout CDP qui corrige précisément l'un des bugs critiques trouvés indépendamment par cet audit. Atelier contient des **éditions locales réelles** (contrairement à ce que son gitignore laissait croire). Plan de réconciliation en 11 étapes ci-dessous.
3. **Côté nouveaux outils, le gisement est mince — et c'est une bonne nouvelle.** Sur 16 candidats générés, le jury adversarial en rejette 12 : la surface actuelle de 38 outils couvre bien le besoin. Survivent 4 idées sous conditions (§D) + 3 extensions S déjà validées par le backlog du 26/06 et jamais livrées.

## A. Correctifs critiques — fiabilité du serveur (P0)

Tous confirmés par lecture contradictoire (3 réfutateurs chacun). Les deux premiers ont été trouvés **indépendamment** par les dimensions concurrence et robustesse.

### A1. Réponse CDP sans timeout → gate MCP figé à vie + fuite `pending` — `adapter-cdp-webview/src/client.rs:217` — **M**
`rx.await` attend indéfiniment une réponse que le navigateur peut ne jamais envoyer (onglet tué, `awaitPromise:true` sur une Promise qui ne se résout jamais — incident réellement vécu côté Chronos le 28/06). Le gate étant tenu pendant l'appel, **tous** les outils MCP sont bloqués.
**Correctif** : `tokio::time::timeout(Duration::from_secs(20), rx)` ; sur expiration, retirer l'entrée de `pending` (sinon fuite) et renvoyer `CdpError::Receive` (qui se mappe déjà vers `PortError::Network` → déclenche le fallback CDP→SDK du mode auto). **Complément** : porter le correctif Chronos `"timeout": 30000` dans le payload `Runtime.evaluate` de `js_evaluator.rs` (borne côté navigateur, cf. §C2-a) — les deux protections se cumulent.

### A2. `LazyCdp::client()` tient le mutex partagé des 5 ports CDP pendant toute la (re)connexion, sans timeout — `deveye-server/src/cdp.rs:76` — **M**
Une cible CDP injoignable (port filtré, handshake WS qui traîne) bloque les 5 ports en cascade.
**Correctif** : `connect_timeout(5s)` + `timeout(10s)` sur le builder reqwest de `CdpClient::connect` (client.rs:125-127), `tokio::time::timeout` autour de `connect_async` ; restructurer `client()` pour relâcher le guard avant l'appel réseau (état « connecting » partagé via `OnceCell` pour éviter les connexions concurrentes).

### A3. `acquire_eis()` (D-Bus `connectToEIS`) et handshake EI sans timeout, dans l'unique worker EIS sérialisé — `adapter-interaction-kwin-eis/src/connection.rs:38-41` — **M**
Un KWin qui ne répond pas fige toutes les interactions OS-level.
**Correctif** : `tokio::time::timeout(5s)` autour de `ZbusConn::session()`, `proxy.connect_to_eis(...)` **et** `context.handshake_tokio(...)`, mappé vers `EisError::Eis(...)` → `PortError::Interaction` propre.

### A4. Lecture du pipe de pixels KWin sans timeout — `adapter-screencap-kwin/src/renderer.rs:190` — **S**
Même famille de gel pour `screenshot`/`screenshot_region`/`assert_visual` sur cible kwin.
**Correctif** : `tokio::time::timeout(5s, reader)` → `KwinScreencapError::Pipe("timeout lecture pipe capture")`. Le thread blocking sous-jacent reste fuité, mais l'appelant et le gate sont libérés.

### A5. `wait_ready`/`wait_condition`/`wait_for_log`/`wait_screenshot_region` abandonnent à la première erreur transitoire — `adapter-mcp-server/src/lib.rs:1223` + `adapter-composite` — **M**
Contredit la raison d'être des outils `wait_*` : une app qui redémarre (le cas d'usage nominal !) fait échouer l'attente au lieu d'être absorbée par le polling.
**Correctif** : généraliser le filtre déjà appliqué à `DomSelector` dans `CompositeWaitCondition::check` — pour `StateKey`/`ScreenshotStable`/`ScreenshotRegionStable`/`LogMessage`, ne propager `Err` que sur `PortError::Network`, sinon `Ok(false)` (continuer). Réécrire `wait_ready` pour déléguer au port `WaitCondition` (il réimplémente aujourd'hui sa propre boucle, hors du refactor L14, sans test — cf. §F).

### A6. `--target kwin-eis` : `.expect("worker EIS")` peut faire paniquer tout le binaire au démarrage — `deveye-server/src/compose.rs:297` — **S**
Seul point de panique hors tests de l'orchestrateur. **Correctif** : propager un `Result` jusqu'à `main()`, sortie propre stderr + exit(1).

### A7. `assert_selector` : `expected_count=0` échoue toujours, même quand l'assertion est vraie — `adapter-mcp-server/src/lib.rs:959` — **S**
Le garde `actual_count >= 1` écrase l'égalité demandée : l'assertion d'absence est inexprimable (trouvé indépendamment par 2 dimensions).
**Correctif** : `let ok = match p.expected_count { Some(n) => actual_count == n, None => actual_count >= 1 };` + test `expected_count: 0`.

### A8. Zéro observabilité là où les gels sont confirmés — `adapter-cdp-webview` (0 tracing), `adapter-mcp-server` (0 tracing) — **M**
Sans une seule trace, un gel en usage réel ne permet pas de savoir **lequel** des 5 ports CDP ou du worker EIS est bloqué. Relevé par la critique de complétude ; aggrave la sévérité de A1-A4.
**Correctif** : instrumenter au minimum : entrée/sortie de chaque commande CDP (id, méthode, durée), acquisition/libération du gate avec le nom de l'outil, cycle de vie EIS (connexion, handshake, dispatch). `tracing` est déjà une dépendance du workspace.

Autres findings du même thème (moyennes, effort S chacun) : `wl-copy`/`wl-paste` attendus sans limite de temps (`adapter-clipboard-wayland/src/lib.rs:37,80`) ; course `take_eval_requests()` (Receiver renvoyé avant enregistrement du Sender, `deveye-sdk/src/lib.rs:281`) ; `Target.attachedToTarget` écrase `session` sans détacher l'ancienne cible pendant un hot-reload (`client.rs:343`) ; verrous SDK non protégés contre l'empoisonnement (`lib.rs:259`) ; `runtime()` du SDK panique si la création du runtime échoue — dans le process de l'**app cible** (`lib.rs:186`, M).

### C1. Régressions Chronos à NE PAS reprendre (trancher en faveur du canonique)
Les 3 commits Chronos du 28/06 ont réinventé une surface déjà présente côté canonique, en **régressant** : `unbounded_channel` au lieu du canal borné `EVAL_QUEUE_CAPACITY=32` (backpressure supprimée) ; CORS deny-all + header `X-DevEye-Protocol-Version` retirés ; `set_state`/`expose_route` devenus asynchrones (la fonction retourne **avant** l'écriture réelle) ; handler de commande exécuté inline sur le runtime mono-thread du SDK au lieu de `spawn_blocking` + catch de panic ; un `spawn` par ligne de log au lieu du drain FIFO unique (optimisation N6 perdue + ordre non garanti).

### C2. Correctifs originaux Chronos à RAPATRIER dans le canonique (avant tout sync)
- **(a)** `"timeout": 30000` dans le payload `Runtime.evaluate` (`adapter-cdp-webview/src/js_evaluator.rs:39-44`) — corrige un incident réellement vécu (« une Promise pendante tenait le gate MCP ») et recoupe A1. **S**

Recoupe le finding api-mcp E1. **M**
- **(d)** Commentaire de convention tracing (`message = ?x` vs `%x`, piège vécu au banc d'essai) dans `tracing_layer.rs`. **S**
